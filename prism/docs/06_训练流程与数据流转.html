0一句话

训练就是：数据从磁盘被切成片段、打包成批、送进 RSSM、算出四项 loss、反向传播更新参数， 循环若干轮（epoch）。

这一页专门讲数据怎么流——每个环节的形状是什么、为什么这么设计。 （loss 本身的细节在笔记 05。）

2完整流转图

从磁盘到参数更新，一共 6 步

3逐步拆解

① Dataset：把一个 episode 切成多个片段

# prism/model/dataset.py  42 行
for s in range(0, T - seq_len + 1, stride):
    self.samples.append((fi, s))        # (哪个文件, 从第几帧开始)
参数默认作用
seq_len32每个片段多少帧
stride8滑窗步长（小于 32 → 片段之间有重叠）
train_ratio0.9前 90% 的 episode 用于训练
一个好设计（第 31–33 行）：train / val 是按 episode 划分的， 不是按片段 —— 避免同一局既用来训练又用来验证。
一个要注意的点：stride=8 < seq_len=32， 所以同一 episode 切出的相邻片段有 24 帧重叠 —— 训练集内的片段并不完全独立。 （验证集因为是不同 episode，所以不受影响。）

② DataLoader：打包成批

每次取 batch_size 个片段，堆成 (B, T, C, H, W)。

③ to_seq_batch：转置成时间在前

# prism/train/train_rssm.py  24 行
images = batch['images'].to(device).permute(1, 0, 2, 3, 4).contiguous()

从 (B,T,...) 转成 (T,B,...)。 为什么：主循环是 for t in range(T)， 这样 images[t] 一次就拿到"所有序列在这一帧的画面" (B,3,64,64)， 既方便又高效（.contiguous() 让内存连续，访问更快）。

④ RSSM：主循环（核心，第 105–122 行）

105  for t in range(T):
106      gru_in = torch.cat([z, actions[t], proprio[t]], dim=-1)    # (B, 46)
107      h = self.gru(gru_in, h)                                    # (B, 200)
109      prior = self.prior_net(h)                                  # (B, 64)
110      mu_p, lv_p = prior.chunk(2, dim=-1)                        # 各 (B, 32)
112      post = self.post_net(torch.cat([h, emb[t]], dim=-1))       # (B, 64)
113      mu_q, lv_q = post.chunk(2, dim=-1)                         # 各 (B, 32)
114      z = self._rsample(mu_q, lv_q)                              # (B, 32)
117      kl = 0.5 * (lv_p - lv_q + (lv_q.exp() + (mu_q-mu_p)**2)
                     / lv_p.exp().clamp(min=1e-4) - 1)
118      kls.append(kl.sum(-1))                                     # (B,)
120      hz = torch.cat([h, z], dim=-1)                             # (B, 232)
121      outs['emb_pred'].append(self.obs_pred(hz))                 # (B, 256)
122      outs['proprio_pred'].append(self.proprio_pred(hz))         # (B, 10)
行在做什么输出形状
106拼 GRU 输入：z（上一帧的）+ 动作 + 本体(B, 46)
107GRU 更新记忆：h[t−1] → h[t](B, 200)
109–110prior（闭卷）：只看 h → mu_p / lv_p(B, 32) ×2
112–113posterior（开卷）：看 h + emb[t] → mu_q / lv_q(B, 32) ×2
114采样出 z —— 只用 posterior(B, 32)
117–118算 KL，并对 32 维求和(B,)
120拼 hz = cat(h, z)(B, 232)
121–122两个预测头：猜画面摘要 / 猜本体(B, 256) / (B, 10)
三个必须注意的点
① z 的时序：106 行用的 z 是上一轮算出来的（t−1）；114 行算出的新 z 供下一轮用。
② prior 是陪练：109–110 算出了 mu_p/lv_p，但 114 行采样只用 posterior； prior 唯一的用处是喂给 117 行的 KL。
③ 循环外还有两次"批量操作"：98–99 行一次性编码全部帧得到 emb； 130 行一次性解码全部帧得到 recon —— 都是为了 GPU 效率。

⑤ loss 与参数更新

losses = rssm_loss(out, images, proprio, kl_weight=..., free_bits=...)
losses['loss'].backward()
torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)   # 梯度裁剪，防爆炸
opt.step()

clip_grad_norm_(..., 1.0)：如果梯度总长度超过 1.0 就按比例缩小 —— RNN 训练的标准做法，防止梯度爆炸。

⑥ 保存权重

每个 epoch 存一次 rssm_epoch{N}.pt（含模型参数 + 训练参数）。

4形状流转总表（核心）

阶段形状说明
磁盘 npz 里(100, 64, 64, 3)一个 episode，HWC 排列，uint8
Dataset 取一个样本(32, 3, 64, 64)转成 CHW，除以 255 → 0~1
DataLoader 打包(16, 32, 3, 64, 64)B=16 条序列
转置后喂 RSSM(32, 16, 3, 64, 64)T 在前
Encoder 输入（合并 T·B）(512, 3, 64, 64)一次性编码 512 张图
emb(32, 16, 256)每帧每序列一个 256 维摘要
循环里 emb[t](16, 256)当前帧、所有序列
h（记忆）(16, 200)16 条序列各一份
z（判断）(16, 32)同上
gru_in(16, 46)z+动作+本体
emb_pred(32, 16, 256)每步收集后堆起来
recon（重建图）(32, 16, 3, 64, 64)一次性解码 512 张
kl(32, 16)已对 32 维求和
B 条序列之间完全独立：各有自己的 h 和 z，互不影响。 B 只是为了并行快和梯度稳，不是把 16 段接成一段长录像。

循环内维度速查表

变量形状含义
images(T, B, 3, 64, 64)一批序列（T 帧 × B 条）
emb(T, B, 256)所有帧的画面摘要
emb[t](B, 256)当前帧、所有序列
h(B, 200)记忆（B 条各一份）
z(B, 32)对当前局面的判断
gru_in(B, 46)z(32) + 动作(4) + 本体(10)
prior / post(B, 64)mu 和 logvar 拼在一起（32+32）
mu_q / lv_q(B, 32)chunk 拆开后
kl(B,)已对 32 维求和
hz(B, 232)h(200) + z(32)
emb_pred[t](B, 256)猜的画面摘要
proprio_pred[t](B, 10)猜的本体状态
recon(T, B, 3, 64, 64)重建出的图像
规律：凡是带 B 的，都是"B 条序列各一份"； 循环里每一步处理的都是"当前帧 × 所有序列"。

补充：代码里的 shape[2:] 和 * 是什么

第 98 行和第 130 行都有这个写法：

images.reshape(T * B, *images.shape[2:])
片段含义例子（shape = (32,16,3,64,64)）
.shape张量的形状（可当元组用）(32, 16, 3, 64, 64)
[2:]切片：取索引 2 及之后的所有元素(3, 64, 64)
*解包：把元组拆成独立参数reshape(512, 3, 64, 64)

所以整句等价于 reshape(512, 3, 64, 64)。

为什么要这么写（而不是直接写 3,64,64）： 换分辨率时代码不用改 —— 如果哪天图像从 64×64 换成 128×128，这一行仍然正确。

5我们实际跑的数字

数据切分全流程（用真实数字走一遍）

668 局（每局 ~80 帧，共 59369 帧）
  ↓ 逐局滑窗（窗口 32、步长 8）
4356 个样本（每个样本 = 32 帧片段；相邻样本重叠 24 帧）
  ↓ shuffle 打乱，每次抓 16 个
一个 batch = 16 个样本 = 16×32 = 512 帧 → 转置成 (32,16,3,64,64)
  ↓ 抓完 272 个 batch
= 1 个 epoch（4356 个样本全过一遍）
  ↓ 重复 20 次
= 完整训练（5440 次 forward+backward）
易混点：backward 的频率是「每个 batch 一次」
上面的「跑完 32 步 → 算总 loss → 一次 backward」说的是一个 batch 内部（32 是时间步数，不是 batch 数）。
每个 batch 都有自己的一次 forward + 一次 backward + 一次参数更新：
1 个 epoch = 272 个 batch = 272 次 backward、272 次参数更新；20 epoch = 5440 次。
不要理解成「一个 epoch 才 backward 一次」。
注意两个易混点：
① 一局滑窗不是 16 次 —— (80−32)/8+1 ≈ 7 次（16 次需要 152 帧，一局只有 ~80 帧）；
② B=16 是跨局抓的 —— 一个 batch 里的 16 个样本来自不同局的不同位置（shuffle 后随机），不是"同一局里连续滑 16 次"。

6三个记忆点

  • images 是 5 维 (T, B, C, H, W)；T=32 帧，B=16 条独立序列
  • B 条序列各自有独立的 h 和 z，互不影响；B 只为了并行和梯度稳定
  • 流转关键一步：permute(1,0,...) 把 (B,T) 转成 (T,B)， 方便主循环一次取一帧

7训练代码 FAQ：疑问与勘误

读 train_rssm.py 时容易卡住的地方，以及之前记错的数字。

疑问答案
out = model(...) 为什么没看到 forward？ Python 的 __call__ 机制：model(x) 自动调用 model.forward(x)。 不要直接写 model.forward(x)——会跳过 PyTorch 的 hooks。
model.train() 哪来的？RSSM 里没定义这个方法 继承自 nn.Module（已验证：RSSM 自己没定义，nn.Module 有）。 它切换训练/评估模式，影响 Dropout / BatchNorm。 我们的模型没有这两种层，所以 train() 实际无影响（写上只是规范）。
eval() 就是推理吗？ eval() 是“推理该用的模式”；完整推理 = model.eval() + with torch.no_grad() + 前向。 两者是不同事：eval 管层行为，no_grad 管梯度（省显存）。
滑窗和 shuffle 在哪？ 滑窗是我们写的（dataset.py：遍历每一局生成 (局索引, 起始帧)）； shuffle 是 DataLoader 的（传 shuffle=True，PyTorch 内部打乱）。
to_seq_batch 是什么函数？ 我们自己写的预处理：.to(device) 搬 GPU + permute(1,0,...) 转置 + contiguous() 连续化。 把 DataLoader 的 (B,T,...) 变成 RSSM 要的 (T,B,...)。
clip_grad_norm_(..., 1.0) 干什么？ 梯度裁剪：把梯度总长度压到 1.0 以内，防止 GRU 沿时间反传时梯度爆炸。 必须在 backward() 之后、step() 之前调用——放错位置就没用。
一个 batch 是 16 个模型吗？ 不是。参数只有 1 份（共享）；数据是 16 份；记忆 h 是 16 份（形状 (16,200)，行与行独立）。 16 份误差平均成 1 个 loss，反向后更新那一套参数。
每一帧都算 loss，还是 32 步才算一次？ 每帧都产生 loss 分量（32 步 × 16 条 = 512 个），但 32 步跑完后 汇总平均成 1 个总 loss，然后 一次 backward（梯度沿 32 步时间链往回传，即 BPTT）。
backward 多久一次？ 每个 batch 一次（不是每个 epoch）。一个 epoch = 272 个 batch = 272 次 backward 与参数更新；20 epoch 共 5440 次。
勘误记录：本页早期版本写的是「928 episode / 7,272 样本 / 454 batch / 一个 epoch 一次 backward」—— 这些都是过时或错误的表述：
① 928/7272/454 是重采前旧数据集（无位姿导出，已备份为 L0_v1）的数字， 当前 L0 为 743 episode / 4356 样本 / 272 batch（见第 5 节）；
② backward 是每个 batch 一次，一个 epoch 共 272 次，不是“一个 epoch 一次”。
